- **新建调查**改为按钮，点击后打开抽屉或模态框，保留现有表单字段、示例问题和防重复提交逻辑。
- **案件列表**用卡片，每项显示：租户名 · 铺位、问题摘要（截断一行）、状态徽标、创建时间。支持本地搜索；窄屏下折叠为顶部下拉。

### 3.2 流程进度条（本次重点之一）

- 横向步骤条：受理 → 分派调查 → 证据核验 → 形成报告 → 物业审批 → 财务审批 → 草案归档。
- 每一步的状态**只能从真实字段推导**（运行状态、report、approval_request 及其 stages）。不能推导的步骤显示“未知”，不能默认已完成。
- 简单查询（只走 billing、无审批）只显示实际经历的步骤，其余步骤显示“本次不涉及”。
- 被驳回、失败、超预算时，步骤条在对应位置显示明确的失败或驳回状态。

### 3.3 结论卡区

四张卡，用业务语言：

1. **争议结论**：如“存在冲突：账单与合同不一致”。来自 verdict 及核验状态，需要复核时明确标出。
2. **金额差异**：如“¥756.00 · 10 月租金多计”。只能取自后端的结构化字段（authoritative_amounts / computed_variance 等），并注明“来源：账单核算”。**审批草案金额（如 ¥700.00）必须单独标注为“预设草案金额，非计算结论”**，不能和差额放在一起暗示因果。
3. **资料缺口**：数量 + 第一条的业务描述，如“附件 B 未电子化”。
4. **下一步**：如“等待物业管理部门审批”“已归档（草案，未执行调账）”。

### 3.4 协作视图

保留 027 的固定职责图和真实状态规则，提升表现力：

- 每个领域节点除状态外，增加**一行关键发现**（业务语言，取自该 Agent 的真实 findings）。例如账单节点写“10 月账单 ¥…，合同应收 ¥…”，没有发现时写“未发现异常”或“本次未调用”。
- 节点上的英文 capability 名（`lease.query`）移到悬停提示或技术视图。
- 连线用柔和的颜色和明确的方向；参与的路径高亮，未参与的路径淡化。

### 3.5 页签内容

1. **案件摘要**：事实 / 推断 / 缺失三段式（保持后端已有的区分）。
2. **冲突对照**（新增）：每个冲突一行，左右并排“合同约定”vs“账单实际”，中间显示差额；每一侧都附证据引用（合同页码与条款号、账单号）。只展示后端 conflicts 中已有的内容，不在前端推算。
3. **证据**：按合同 / 账单 / 工单分组。合同证据显示条款号、页码、原文摘录（引用块样式）；账单用表格；工单用时间线。
4. **审批单**（重做）：做成审批单样式——草案摘要、金额（标注为预设草案）、两级审批时间线（角色中文名、审批人、决定、时间、意见）。只有当前轮到的审批角色显示“批准 / 驳回”按钮，并带意见输入框。归档后显示醒目提示“已批准草案 · 未执行任何调账或减免”。
5. **技术视图**：保留现有的调用记录、Trace、原始 JSON、字段名和 run_id。默认折叠，面向开发和复查。

## 4. 真实性规则（继承 027，本任务不得削弱）

- 请求进行中只显示“调查执行中”，不伪造逐节点进度、思考过程、token 或耗时；不用 setTimeout 演出“依次完成”。
- `completed` 不等于“争议解决”；`awaiting_approval` 不等于结案；`conflicting` 和部分完成不能显示为全绿。
- 字段缺失、类型异常、未知状态一律显示“未提供 / 待核实 / 需复核”，**不能默认成功或 0**。
- 金额只展示后端结构化字段，不做减免后余额之类的计算。
- 所有用户输入、证据摘录和错误信息必须安全渲染（`textContent` 或统一转义），不拼接未转义的 innerHTML。
- 前端不发送自报身份字段，不暴露 `.env`。
- 快速切换案件时旧响应不能覆盖新案件（请求序号或 AbortController）。

## 6. 视觉设计规范

目标是专业、克制、可信，像金融或企业服务的后台产品，不像炫技的演示页。

**颜色（在 workbench.css 里用 CSS 变量统一定义）**
- 页面底色：很浅的冷灰（接近 `#F5F7FA`）；卡片为白色，用 1px 浅边框，阴影极轻或不用。
- 主色：一种沉稳的深蓝，只用于主要按钮、选中态和当前步骤。
- 领域辅助色（只用于节点左侧色条和小图标，不大面积铺色）：合同 = 靛蓝，账单 = 青绿，物业 = 橙棕，知识检索 = 紫。
- 语义色：成功 = 绿，警告 / 部分 = 琥珀，失败 / 驳回 = 红，未知 = 灰。**每个状态都必须同时有文字和图标**，不能只靠颜色。
- 全页的高饱和色块不超过 3 处。

**字体与排版**
- 字体栈：`-apple-system, "PingFang SC", "Microsoft YaHei", "Segoe UI", sans-serif`。
- 字号阶梯只用：12 / 13 / 14 / 16 / 20 / 24 px。正文 14px，案件标题 20px，结论卡数字 24px。
- 字重只用 400 和 600。
- 所有金额、数量、日期使用 `font-variant-numeric: tabular-nums`。

**金额显示**
- 格式：`¥18,036.00`。**用字符串处理加千分位，严禁 `parseFloat`、`Number()` 等转成浮点数再格式化**，后端给的是精确的十进制字符串。
- 金额在表格中右对齐。差额用颜色 + 正负号 + 文字（“多计”/“少计”）三重表达。

**间距与形状**
- 8px 网格：间距只用 4 / 8 / 12 / 16 / 24 / 32。
- 圆角：卡片 8px，徽标 4px。
- 每张卡片只有一个主标题，层级不超过三级。

**动效**
- 只做 150–200ms 的淡入、展开和颜色过渡；`prefers-reduced-motion` 下全部关闭。

**文案**
- 主视图里不出现英文枚举、内部字段名或 ID。建立一个集中的术语映射表（`js/i18n.js` 或类似文件），所有状态和字段都通过它转换；映射缺失时显示“未知状态（原值）”，不能空白。
- 人员显示中文角色名（如“财务部门 · 财务复核人”），ID 只放在技术视图和悬停提示里。
- 所有页面文案标注合成数据，例如租户名保留数据中原有的“（合成租户）”字样。

## 7. 验收

### 7.1 “5 秒测试”（最重要）

一个不懂技术的人看 1440×900 首屏 5 秒，必须能回答：
1. 这是哪个租户、哪个铺位的什么问题？
2. 有没有冲突？差多少钱？
3. 现在流程走到哪一步，下一步等谁？
4. 结论有没有需要人工复核的地方？

在归档里用截图逐条说明首屏上各问题的答案在哪里。

### 7.2 截图（真实运行，不能 mock）

用临时的控制面目录和数据，不修改用户已有的运行记录，至少产出以下截图，保存到 `docs/reviews/task032_screenshots/`：

1. A-301 复杂调查（存在冲突，待物业审批）首屏，1440×900
2. 同一案件的“冲突对照”页签
3. 同一案件的“证据”页签（含合同摘录）
4. 物业审批通过后、等待财务审批

6. 被驳回的案件
7. 简单账单查询（只有账单节点参与，步骤条显示“本次不涉及”）
