### F1：账单查询把项目内其他租约的付款计入当前租约

**位置**：`backend/app/fixtures/repository.py` 的 `FixtureRepository.statement()`。

查询先按 `lease_id` 限定 invoices，但 `confirmed_payments`、`allocations`、`valid_payments` 后续只按 `project_ids` 筛选。结果会把同项目其他租约的付款/核销放进当前租约 Statement，并用其金额减少当前未收款。

**Codex 复现**：在 fixture 内存副本追加同项目 A-302 的账单、确认付款 `100.00` 和核销；调用 A-301 Statement 后得到 `paid_total=34660.00`，且返回了 `alloc_test_a302`。A-301 原付款合计应为 `34560.00`，未收应为 `18036.00`。

**要求**：严格按当前租约的 invoice IDs 过滤 allocations；只返回关联到这些 allocations 的 confirmed payments；保持冲销记录不参与；新增同项目另一租约的独立付款回归测试，断言 A-301 金额、payment 和 allocation 列表不受 A-302 影响。

### F2：复用 Runtime 后结果 Trace 混入先前运行

**位置**：`backend/app/runtime/agent_runtime.py` 的 `AgentRuntime.run()` 和 `TraceLog` 快照用法。

**Codex 复现**：同一个 `build_demo_bundle()` 连续执行两次 `run_demo(bundle)`；第一次结果有 3 条 Trace，第二次有 6 条，因为 Runtime 返回进程级累计的 `TraceLog.snapshot()`。这会把过往调用混入当前 run 的评测结果。

**要求**：每个 `RuntimeResult.tool_traces` 只包含当前 `run_id` 本次执行产生的调用；保留可共享的 append-only TraceLog 能力以便后续全局可观测，但给本次 run 明确边界（例如按本次 trace_id / 调用起始偏移截取，或显式关联 run_id）。加入同一 Runtime 至少连续两次调用的测试，断言结果间无 Trace 重复或交叉，且全局 TraceLog 仍保留全部 Trace。避免仅清空共享日志导致并发 run 丢数据。
