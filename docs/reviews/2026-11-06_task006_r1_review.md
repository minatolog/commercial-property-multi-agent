## 2. 阻塞项

### R1-R2 — 场景选择协议与 JSONL 结构不匹配

`evaluation_plan.md` §2.3 和 fixture 的 `scenario_protocol.resolution_order` 写的是 `case.scenarios[case.scenario_id]`。实际 C06/C08 JSONL 没有顶层 `scenario_id`，`scenarios` 是数组，不是以 ID 为键的对象；C01–C05、C07 没有 `scenarios` 字段。因而按文档实现的 runner 无法选中 `main_timeout_exhausted`、`recovery_probe` 或 C08 六种审批路径。DeepSeek 的验证脚本只比对 case 与 fixture 中同名场景是否存在/一致，没有验证场景选择表达式可按实际 JSON 结构求值。

**要求**：定义一致、可执行的场景运行语义。建议 runner 将含 `scenarios` 的 case 展开成 `(case_id, scenario_id)` 独立运行项；按 `scenario_id` 在 case 的场景数组中匹配期望断言，再用同一 ID 从所引用 variant 的 `scenarios` 映射选出事件。无场景 case 运行一次并沿用 variant 默认事件语义。未知或重复 ID 必须报验证错误。若选择其他数据结构，需同步 JSONL、fixture、评测计划与校验器。加入针对 C06 两路径、C08 六路径及普通 case 的真实选择器测试断言。

### R3-R4 — 审批重放事件内容并不相同

`v_approval_flow.scenarios.approval_replay.events` 中 `evt_apr_fin_grant_003` 第二次出现时多了 `"replayed": true`。契约 §9.2、§12.6 明确规定：相同 `event_id` 且内容相同才幂等；相同 ID、不同内容必须产生 `EVENT_ID_CONFLICT`。当前 fixture 同时要求 `duplicate_events_ignored=1`，与自身事件契约矛盾。

**要求**：第二次事件必须逐字段与原事件完全一致（删除 replay 标记），由场景的到达次数/注入配置表达重复投递。校验器应比较同 ID 事件的规范化内容，确认该场景恰有一组完全相同的重复项，并补一条同 ID 异内容必须冲突的负例断言。不能把 `replayed` 当成事件来源字段来豁免内容哈希。
