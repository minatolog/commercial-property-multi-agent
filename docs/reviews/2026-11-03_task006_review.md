## 3. 必须修正：R1 — 超时用例无法按当前通用规则验收（高）

**位置**：[C06](../evaluation/cases/smoke_v1.jsonl) 第 6 行；[评测计划](../evaluation/evaluation_plan.md) §2.3、§2.5。

C06 配置同一工具前两次超时、最多调用两次，主路径预期失败或降级；却无条件要求返回三张 invoice 证据。来源在 fixture 中存在，不代表工具失败时 Agent 能取得。通用“全部 required 必须命中”规则与失败路径冲突。

此外，probe 使用 fail_attempts=1，但注册事件仍是 2；审批子变体、probe 和主事件的覆盖顺序没有正式解析协议。

**修正要求**：主失败路径与恢复 probe 分开定义条件断言和证据要求；明确 scenario 解析顺序。失败路径不得因缺失工具结果被强迫读取隐藏数据，probe 才要求恢复后的证据。

## 4. 必须修正：R2–R6

### R2 — 三基线比较被路由标签预先决定（高）

**位置**：[评测计划](../evaluation/evaluation_plan.md) §3、§4.1、§5.1；C03/C04/C08 的 allowed_routes。

三基线要回答相同问题，但当前 C03/C04/C08 只允许 multi_agent；若用同一套断言评价 A/B，正确答案仍必然路由失败，不能作为公平质量对照。C04 是单主题合同冲突，一个 Lease Agent + Verifier 完全可能处理，不能预设“多 Agent 必要”。C01 允许 deterministic/single_agent，某条断言 expected 却只写 deterministic；C05 摘要与允许集合也不一致。

**修正要求**：事实、引用、权限、审批为共通质量指标；编排约束按 baseline_mode 分开；默认产品路由作为独立效率指标。允许简单方案解决复杂题，不将不同基线的架构身份判为答案错误。用一份假想正确结构化结果说明 A/B/C 如何分别评分，不调用模型。

### R3 — 审批成功路径缺少可验证的授权事件（高）

**位置**：fixture.principals、variant_registry.v_approval_flow；C08；[契约](../architecture/agent_runtime_contracts.md) §12。

现有主体仅有 approval.request，无审批角色或 approval.decide；C08 只给 decision=granted，未给可信审批人、角色、草案版本和事件 ID。又要求物业与财务角色，尚不明确 AND/OR、谁先批、一个人能否完成。不能让模型生成的 granted 或客户端自报角色视为授权。

**修正要求**：提供合成且可信的审批主体和显式事件序列；定义角色规则与状态转移；补无权限审批、正确版本授权、同版本重放、换版拒绝、过期拒绝的可解析场景。允许采用简单串行审批，不建设复杂审批平台。保持只批准草案、不真实调账。

### R4 — 重放与并发归并规则仍有自相矛盾（高）

**位置**：[契约](../architecture/agent_runtime_contracts.md) §9.1–9.2、§10。

attempt 虽去重，budget_used 仍简单相加，重放可重复计费；Evidence 同 ID “后写覆盖”并记录当前时间会因并发到达顺序产生不同结果。wall_clock 若按并发节点相加，则不是任务墙钟耗时。Runtime 预算 reserve/consume 尚缺原子性和重放标识语义。

**修正要求**：明确稳定调用/事件 ID、预算记账去重、原子预留/结算；同一 ID 相同内容可幂等合并，不同内容报冲突或形成明确版本，禁止按到达顺序隐式覆盖；任务墙钟用单调时钟的实际经过时间，节点耗时可另统计。写出相反到达顺序和重放的输入/预期例子。

### R5 — Graph 分支和证据契约尚未闭合（高）

**位置**：[契约](../architecture/agent_runtime_contracts.md) §3、§9、§11–12。

- verify 缺少 insufficient 且可补查、conflicting 且上限已到的完整去向。
- plan 声称只有 planner 写，revise 却追加子任务；需要明确回到 planner 或调整唯一写入规则。
- 信息不足被送入 approval，混淆“需要人补充事实”和“批准某个动作草案”。没有动作草案时不应索取减免审批。
- report → approval 后的最终结果如何包含审批状态、拒绝理由尚未明确。
- Evidence 缺少基线要求的数据版本字段；ToolResult 没定义其证据输出，Finding 引用 computation 但无完整类型。只列“关键字段”不足以作为这些关键对象的编码级规格。

**修正要求**：用穷尽表定义 verifier/revise/report/approval 的转移，必需人工补充与动作审批分开；明确 State 写入者；补 Evidence 数据版本、ToolResult evidence、computation、工作流状态枚举及关键约束。resume 文案不承诺永远只从下一节点开始，应容纳重放，并写清如何保证结果幂等。

### R6 — P0/P1 范围和审计记录需要统一（中）

**位置**：[MVP](../product/mvp_scope_v2.md) §3、§6；[评测计划](../evaluation/evaluation_plan.md) §6；006 §8。

- 最终 P0 要 30–50 题和客观对照，保留集却被整体放入 P1。
- MVP 要 agent_runs 记录指标，但该表尚无当前 P0 实施决策，应要求 Trace 记录，存储方案单独决定。
- “只能跑一次”不利于测量模型随机性；应禁止看结果后调参，允许预先固定重复次数并冻结配置。
- K6 在无数据库模型阶段不是已复现运行时 bug，应移为未来数据库映射注意事项。
- 006 §8 仍说 DeepSeek 尚未执行，与执行记录冲突；目录枚举+大小不能宣称 byte-identical。
- 执行计划不要为了现有占位类型预先实现三套兼容生命周期；允许受控增量迁移，明确必须保留的接口和回归范围即可。
