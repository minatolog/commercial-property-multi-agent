## 5. 设计要点

### 5.1 薄外壳与唯一执行入口

- `tools/list` 只列**当前客户端档案允许的只读工具**，顺序与档案一致；`inputSchema` 来自 `input_model.model_json_schema()`，`outputSchema` 是统一结果信封（`data` 部分来自 `output_model`）。
- 工具名同时提供下划线别名（`billing.statement.read` → `billing_statement_read`）。别名冲突（别名之间或别名与原名重叠）在构建 `Server` 时抛 `AgentConfigError`，启动失败，而不是静默覆盖。
- `tools/call` 的顺序固定：保留键拦截 → 别名映射回原名 → 从**会话身份**构造 `AgentContext` → `ToolExecutor.execute()` → 结果信封。网关不写第二套白名单、权限或预算逻辑。
- Trace 记录原名；会话 ID 形如 `mcp_<档案名>_<随机串>`，写入 `run_id`，因此 Trace 中可同时看到 `entrypoint=mcp`（前缀）与 `client=<档案名>`（第二段）。

### 5.2 SDK 版本与 low-level `Server` 的实际用法

`mcp==2.3.0` 的 low-level `Server` 使用**构造函数回调**（不是 v1 的装饰器写法）：

```python
Server(
    name=GATEWAY_NAME,
    version=GATEWAY_VERSION,
    instructions=...,
    lifespan=self._lifespan,          # 每个连接一个 McpSession
    on_list_tools=self._on_list_tools,
    on_call_tool=self._on_call_tool,
)
```

stdio 入口使用 `mcp.server.stdio.stdio_server()` 取得读写流，再调用：

```python
await server.run(read_stream, write_stream, server.create_initialization_options())
```

处理器参数与结果类型来自 `mcp_types`；`ctx.lifespan_context` 即当前连接的 `McpSession`。测试用 `Client(server, mode="legacy")` 走内存传输；手动连接脚本用 `ClientSession` + `stdio_client` 启动真实子进程。

### 5.3 会话、身份与预算

- **一个 MCP 连接一个会话**：`_lifespan` 为每个连接新建 `SessionIdentity`、`Budget`、`ToolExecutor`、`TraceLog`，连接之间互不共享；重连按档案额度重新计算。
- 开发模式下主体来自客户端档案的 `principal_id`；环境变量 `DEMO_PRINCIPAL_ID` 非空时覆盖，`SessionIdentity.source` 如实记录 `profile` 或 `env:DEMO_PRINCIPAL_ID`。
- `resolve_context(session)` 只读取会话身份与**服务端** fixture 主体记录；`project_ids` / `permissions` 来自主体记录，绝不从 `tools/call` 参数读取。
- 启动时向 stderr 打印“开发模式：固定主体，不可用于生产”；stdout 只承载 MCP 协议。

### 5.4 客户端档案

- pydantic `extra="forbid"`：档案里多写字段（例如 `api_key`）在加载期直接失败。
- 只读白名单是独立于注册表的硬约束：即使将来注册了写工具，档案列出它也会被拒绝。
- 档案名必须与文件名一致；被禁用、列出未注册或非只读工具都会在启动期失败，并点名具体档案与工具。
- `local_dev` 开放全部 5 个只读工具（含 `billing.arrears.calculate`）；`flowise` 只开放 4 个，不含 `billing.arrears.calculate`。两者开发主体均为 `principal_ops_xinghui`，每会话预算 20 次，区别只在工具白名单。

### 5.5 结果信封

- 成功与失败都返回同一信封：`call_id` / `status` / `data` / `evidence` / `error`，同时放进 `structuredContent` 与一条 JSON 文本 `content`，两者逐字节同源。
- 只有执行器判定成功才是 `ok`；保留键、未知/未授权工具、身份解析失败、超时、预算耗尽与未预期异常都以 `isError: true` 返回，并带执行器错误码。网关自身的异常只在 stderr 记录堆栈，不把 Python 堆栈返回客户端。
- 金额全程保持十进制字符串（例如 `"40000.00"`、`"120.0000"`）；输出 Schema 中 `Decimal` 固定声明为 `string`，失败信封的 `data` 允许为 `null`。

## 8. 安全边界

- **只读**：本版只开放 `lease.lookup`、`billing.statement.read`、`billing.arrears.calculate`、`property.work_orders.read`、`document.search`；写工具即使注册也会被档案校验拒绝。
- **身份只来自服务端会话**：`AgentContext` 只能由 `resolve_context(session)` 从会话身份与 fixture 主体记录构造；`principal_id`、`permissions`、`project_ids` 等保留键出现在调用参数中直接拒绝。
- **保留键拦截**：`RESERVED_PAYLOAD_KEYS` 中的键在进入执行器前被网关拒绝，返回 `permission_denied` / `denied`。
- **预算按会话**：每个 MCP 连接一个独立 `Budget`，额度来自客户端档案；重连重新计算，不能跨连接共享或透支。
- **开发模式固定主体不可用于生产**：本版没有令牌校验，启动即向 stderr 明确告警；档案主体或 `DEMO_PRINCIPAL_ID` 只是开发身份，不是认证。
- **失败不伪装成功**：所有失败返回 `isError: true`；未知状态或矛盾状态（例如 `status=ok` 但带错误详情）一律落为 `error`。
- **不提供任意能力**：网关不提供 SQL / Python / Shell / 文件系统 / 网络工具；`document.search` 的文档正文只作为不可信返回值。
- **诊断信息不污染协议**：stdout 只承载 MCP 协议，开发模式提示与异常堆栈只写 stderr。

## 9. 遗留问题与下一版风险

### 9.1 遗留问题

- **未接入 Flowise 运行时**：只在文档中给出 stdio 配置方式，没有用 Flowise 实际连接；本轮的手动验证使用 SDK 客户端。
- **未使用 MCP Inspector**：原 Prompt 允许 Inspector 或 SDK 客户端二选一，本轮选 SDK 客户端；两者都没有覆盖的客户端兼容性仍需外部客户端实测。
- **没有 HTTP 传输、没有 OAuth、没有 TLS**：身份仍是开发模式固定主体，不能用于生产。
- **未跑真实外部客户端的长连接/重连场景**：内存测试与一次 stdio 子进程冒烟覆盖了协议外壳，但不等于真实 MCP 客户端的全部行为。
- **客户端对 Schema 的严格程度未知**：网关的失败信封把 `data` 置为 `null`，Schema 已声明可空；如果某个外部客户端强制要求 `data` 为对象，需要客户端侧适配或协议层再评估。

### 9.2 下一版（Streamable HTTP + OAuth）最大的风险

**身份与传输会话的生命周期错配。** 当前实现把“连接 = 会话 = 一个固定主体 + 独立预算”写死在 `lifespan` 里；Streamable HTTP 下这三者不再一一对应：同一进程会承载多个客户端，`Mcp-Session-Id` 可以恢复/重连，单会话内还有并发请求。如果下一版只是把 `create_session` 里的“信任档案/环境变量”换成“解析 OAuth 令牌”，而仍然把 `AgentContext`、`Budget`、`ToolExecutor` 缓存在传输会话或 `lifespan` 上，就会出现具体越权场景：客户端 A 用旧 `Mcp-Session-Id` 重连、或客户端 B 拿着自己的令牌恢复同一会话时，请求可能复用上一个主体的项目范围与预算；反过来，每次请求重新解析令牌却不校验会话归属，也会让会话 ID 成为可猜测的越权入口。

因此下一版必须做到：令牌在**每次请求**验证（签名、`iss`、`aud`、`exp`/`nbf`、时钟偏移），主体映射到 fixture 主体记录后才构造 `AgentContext`；`Mcp-Session-Id` 在创建时绑定令牌主体，恢复时必须重新认证且主体一致；`Budget` 按“已认证会话”而不是 TCP 连接计数；JWKS 拉取失败必须 fail-closed，不能降级成匿名或开发主体；并彻底移除 `DEMO_PRINCIPAL_ID` 在 HTTP 路径上的兜底。否则协议外壳看起来接上了 OAuth，实际仍可能在会话复用处把 A 的权限交给 B。
